## 1. 文档目的

本文档用于统一知光项目后续开发方向、业务边界、技术约束、交付顺序和验收标准。

知光不以堆叠技术组件为目标，而是建设一个可以完整演示、可靠运行、能够经受代码审查和面试追问的知识社区项目。后续开发分为两条主线：

1. 传统业务：补齐知识社区 CRUD、权限、状态、事务、并发、审计和治理闭环。
2. AI 业务：建设面向创作和学习场景的轻量化 Agent，RAG 保留为 Agent 的可信检索工具，不再作为孤立产品。

## 2. 产品定位

知光是一个以“知文”为核心内容载体的轻量知识社区。

当前形态接近文章型知乎，支持用户发布知识内容、浏览 Feed、搜索、点赞收藏、关注作者，并使用 AI 辅助创作和学习。

第一阶段不复制完整的知乎问答模型，不立即引入 Question/Answer 聚合；优先把文章型知识社区做完整。问题—回答、付费内容、私信等能力作为后续扩展。

### 2.1 目标用户

- 希望整理和发布技术、学习、经验类内容的创作者。
- 希望检索、阅读并系统学习知识的普通用户。
- 负责内容审核、举报处理和平台运营的管理员。

### 2.2 核心业务主线

```text
用户认证
  ↓
创建草稿
  ↓
OSS 预签名直传
  ↓
发布事务
  ├─ MySQL 知文数据
  └─ Outbox 事件
       ↓ Canal / Kafka
       ├─ Elasticsearch 搜索索引
       ├─ RAG 向量索引
       ├─ Feed 缓存失效
       ├─ 通知
       └─ 统计
  ↓
搜索、阅读、AI 问答
  ↓
点赞、收藏、评论、关注
  ↓
Redis + Kafka 聚合计数
```

## 3. 项目级开发约束

### 3.1 架构约束

- 保持单个 Spring Boot 应用，建设模块化单体。
- 当前阶段不拆微服务，不引入 API Gateway。
- 中间件和应用优先通过 Docker Compose 运行。
- Docker 数据、依赖缓存和项目文件优先保存在 E 盘工作区。
- 外部系统调用不得在数据库事务中长时间阻塞。
- 不为了展示技术而增加无业务价值的基础设施。

### 3.2 Java 代码约束

- 根包名统一使用 `com.chuanqing`。
- 使用普通 `class`、`interface` 和 `enum`，不使用 Java `record`。
- 顶层结构保持：Controller、Service、Entity、Mapper、DTO、VO、Config、Utils、Exception。
- 在顶层分层之下，按照业务域建立子包，例如 `controller.knowpost`、`service.knowpost`。
- Controller 类必须以 `Controller` 结尾，其他类也必须使用能体现业务上下文与职责的完整名称。
- Controller 只负责 HTTP 协议、参数校验、身份提取和响应转换。
- Service 负责业务用例和事务边界。
- Mapper 只负责数据访问，不承载业务规则。
- DTO 只用于入参，VO 只用于出参，Entity 不直接暴露给前端。
- 正式接口不得使用 `Map<String, Object>` 代替明确的 VO。
- 业务状态、类型和动作优先使用 enum，不使用散落的字符串常量。

### 3.3 Git 约束

- `dev`：日常开发分支。
- `main`：阶段性可运行版本。
- `master`：暂时保留，不作为后续日常开发入口。
- 每一批提交必须能独立编译，并完成与风险相匹配的验证。

## 4. 当前系统概况

当前后端已经具备以下能力：

- JWT 双令牌认证、Redis Refresh Token 白名单。
- 手机号或邮箱注册、登录、验证码与密码重置。
- 用户资料和头像上传。
- 知文草稿、OSS 直传、元数据编辑、发布、软删除。
- 公共 Feed 和个人发布列表。
- Redis 位图点赞收藏、Kafka 异步聚合、SDS 计数。
- 关注取关、粉丝列表、Outbox + Canal + Kafka 同步。
- Elasticsearch 全文搜索和联想建议。
- AI 摘要。
- 单篇知文 RAG 问答。

当前主要问题不是缺少技术组件，而是业务完整性、可靠性、测试和可观测性不足。

## 5. 总体建设目标

### 5.1 传统业务目标

- 知文具有明确、可校验、可审计的生命周期。
- 所有权限规则在详情、Feed、搜索、RAG 中保持一致。
- 写操作具备正确事务边界、幂等性和并发控制。
- 异步事件可以重试、去重、重放和监控。
- 补齐评论、通知、收藏夹、话题、阅读历史和举报审核。
- 数据库结构通过迁移脚本持续演进。
- 核心业务具备真实中间件集成测试。

### 5.2 AI 业务目标

- 建设“知文学习与创作助理”，而不是通用聊天机器人。
- AI 能调用站内只读工具和有限写工具完成多步骤任务。
- RAG 成为可信检索工具，支持过滤、混合召回、引用和评测。
- 模型接入与业务解耦，支持 Qwen、Pico 等提供方按能力路由。
- 所有 Agent 写操作遵守现有 Service 的权限、事务和幂等规则。
- 建立调用成本、耗时、工具选择、任务完成率和安全性评测。

## 7. 传统业务需求

## 7.1 P0：修复现有核心链路

### 7.1.1 知文状态机

状态定义：

```text
DRAFT → PENDING_REVIEW → PUBLISHED → OFFLINE → DELETED
                  ↘ REJECTED → DRAFT
```

第一阶段允许暂不启用人工审核，但状态模型必须支持扩展。

要求：

- 状态使用 `KnowPostStatusEnums`。
- 发布只允许从合法原状态进入 `PUBLISHED`。
- 重复发布不得重复增加发文数或重复产生业务副作用。
- 删除只允许发生一次；重复删除返回幂等成功或明确冲突。
- 发布前校验标题、正文、摘要、可见性等必需信息。
- 状态更新 SQL 必须携带原状态条件。
- 状态冲突返回 HTTP 409。
- 关键状态变化记录操作日志。

验收标准：

- 并发发布同一草稿时最多一次成功。
- 重复请求不会重复增加计数。
- 已删除内容不能再次发布。
- 对应单元测试和 MySQL 集成测试通过。

### 7.1.2 可见性权限

定义 `KnowPostVisibilityEnums`：

- `PUBLIC`：所有人可见。
- `FOLLOWERS`：关注作者的用户可见。
- `SCHOOL`：与作者学校相同的用户可见。
- `PRIVATE`：仅作者可见。
- `UNLISTED`：持有链接可访问，但不出现在 Feed 和搜索中。

要求：

- 建立统一的 `KnowPostPermissionService`。
- 详情、Feed、搜索、RAG 使用同一套权限规则。
- 非公开内容不得通过搜索索引或缓存泄漏。
- 权限不足返回 HTTP 403，内容不存在返回 HTTP 404。

### 7.1.3 Outbox 事务一致性

要求：

- 业务写入和 Outbox 写入处于同一 MySQL 事务。
- Outbox 写入异常不得被吞掉。
- 事件至少包含事件 ID、类型、版本、聚合 ID、发生时间、Trace ID 和 Payload。
- Canal 到 Kafka 的发送必须确认成功后再推进位点。
- 消费者必须幂等。
- 消费失败支持重试、死信和人工重放。

### 7.1.4 关注取关幂等

要求：

- 禁止关注自己。
- 验证目标用户存在。
- 只有 `未关注 → 已关注` 才产生 FollowCreated。
- 只有 `已关注 → 未关注` 才产生 FollowCanceled。
- 使用统一雪花 ID。
- 重复操作不得重复修改关注数和粉丝数。

### 7.1.5 点赞收藏完整性

要求：

- `entityType` 使用枚举和白名单。
- 操作前校验目标实体存在且用户可访问。
- 保留内容维度位图以提供高性能状态判断。
- 增加用户维度反向索引，支持“我的点赞”和“我的收藏”。
- Kafka 发送失败不得静默丢失。
- 计数可根据事实数据重建。
- Redis `KEYS` 替换为索引集合或 `SCAN`。

### 7.1.6 OSS 文件生命周期

新增 `storage_objects`，状态包括：

```text
PRESIGNED → UPLOADED → CONFIRMED → REFERENCED
                         ↘ ORPHANED → DELETED
```

要求：

- 文件大小、MIME 和扩展名白名单。
- objectKey 必须属于当前用户和当前业务对象。
- 确认上传时通过 OSS HEAD 校验大小、ETag 等信息。
- 定时清理未确认和未引用文件。
- 删除业务对象后延迟清理文件。

### 7.1.7 API、异常与数据库迁移

要求：

- 引入 Flyway 管理数据库变更。
- 统一分页结构和错误响应。
- 区分 400、401、403、404、409、429、500。
- 正式接口使用明确 DTO/VO。
- 重要写操作增加必要的乐观锁或原状态条件。
- OpenAPI 文档与代码保持一致。

## 7.2 P1：补齐社区闭环

### 7.2.1 评论与回复

- 删除评论保留必要占位，避免回复链断裂。
- 评论产生通知和计数事件。

```text

POST_FAVORITE
COMMENT

COMMENT_LIKE
REVIEW_RESULT
SYSTEM
```

支持通知列表、未读数量、单条已读、全部已读、通知聚合和通知偏好。

### 7.2.3 收藏夹与行为列表

- 我的点赞。
- 我的收藏。
- 自定义收藏夹。
- 收藏夹内容移动和删除。
- 内容删除或下架后的失效提示。

### 7.2.4 话题与标签

- 话题创建、检索、关注和内容列表。
- `know_post_topics` 建立规范关系。

- 支持热门话题和同义话题合并。

### 7.2.5 浏览历史与阅读进度

- 停留时长和是否读完。
- 清除历史。
- 为推荐和学习 Agent 提供行为依据。

### 7.2.6 举报与审核

- 支持举报知文、评论和用户。
- 支持审核通过、驳回、下架、恢复、警告和封禁。
- 所有管理员操作记录审计日志。
- AI 只提供辅助判断，不直接决定最终业务状态。

## 8. AI 产品需求

## 8.1 AI 产品定位

AI 模块定位为“知文学习与创作助理”，包括两条核心工作流。

### 8.1.1 创作者工作流

```text
输入 Markdown 或创作目标
→ 分析内容
→ 生成标题、摘要、标签和大纲
→ 检查质量与风险
→ 创建或修改草稿
→ 生成发布预览
→ 用户确认
→ 发布
```

### 8.1.2 学习者工作流

```text
输入学习目标
→ 搜索站内知文
→ 筛选内容
→ 生成学习顺序
→ 解释知识
→ 生成测验与知识卡片
→ 保存学习计划
→ 根据学习结果调整计划
```

## 8.2 轻量 Agent 约束

- Agent 只处理站内知识创作和学习场景。
- 不建设无限循环或无限自主执行的通用 Agent。
- 单次运行默认最多执行 5～8 个步骤。
- AgentTool 只能调用业务 Service，不能直接调用 Mapper。
- 工具调用必须继承当前用户身份和权限。
- 每次运行记录模型、Prompt 版本、工具调用、耗时、Token 和结果状态。

运行状态：

```text
RECEIVED
PLANNING
TOOL_CALLING
WAITING_CONFIRMATION
RESPONDING
COMPLETED
FAILED
CANCELED
```

## 8.3 Agent 工具分级

### 只读工具

- 搜索知文。
- 查询知文详情。
- 检索 RAG 上下文。
- 查询话题和标签。
- 查询学习记录和用户学习画像。

只读工具可以由 Agent 自动执行。

### 可恢复写工具

- 创建草稿。
- 修改草稿。
- 创建知识卡片。
- 保存学习计划。
- 更新学习进度。

工具执行后必须向用户清晰展示变更。

### 正式或敏感工具

- 发布知文。
- 删除知文。
- 覆盖正文。
- 修改可见性。
- 批量操作。

此类操作必须进入 `WAITING_CONFIRMATION`，收到明确确认后才能执行。

## 8.4 模型抽象与路由

建立统一模型接口：

```text
AiModelService
├─ QwenAiModelServiceImpl
└─ PicoAiModelServiceImpl
```

由 `AiModelRouterService` 根据任务选择模型：

- 意图识别：快速、低成本模型。
- 工具调用：支持可靠结构化输出的模型。
- 标题、摘要、标签：快速模型。
- 跨文章研究和最终综合：能力更强的模型。
- Embedding：独立向量模型。
- Rerank：独立重排模型或评分服务。

业务 Service 不直接依赖具体提供方的 Options 类型。

## 8.5 RAG 新定位

RAG 保留为 Agent 的可信检索工具，必须完成以下升级：

- 检索阶段直接按 postId、可见性、作者和话题过滤。
- BM25 与向量混合召回。
- Query Rewrite 和复杂问题拆分。
- Rerank。
- 相似度阈值。
- 上下文压缩。
- 返回引用段落和来源。
- 无依据时明确拒答。
- 索引构建异步化。
- 索引状态可查询、可重试、可重建。

暂不引入 GraphRAG 和多 Agent，除非后续数据规模与评测结果能够证明必要性。

## 8.6 Agent 最小数据模型

第一阶段计划新增：

```text
ai_session
ai_message
ai_run
ai_tool_call
user_learning_profile
learning_card
learning_plan
```

长期记忆保存结构化学习偏好和事实，不把所有聊天原文直接作为永久记忆。

## 8.7 Agent SSE 协议

流式事件类型：

```text
planning
tool_started
tool_completed
content
citation
waiting_confirmation
done
error
```

前端应展示 Agent 当前步骤，不只显示最终文本。

## 9. 非功能要求

## 9.1 安全

- 轮换已经暴露的 OSS AccessKey。
- JWT 校验 issuer、签名、过期时间和令牌类型。
- CORS 使用环境化白名单。
- AI 接口要求登录、限流和每日额度。
- 上传接口限制大小和类型。
- 管理接口使用明确角色权限。
- 敏感配置不得进入 Git、日志和接口响应。
- Agent 必须防止越权工具调用和提示词注入。

## 9.2 测试

- Service 单元测试。
- Mapper + MySQL 集成测试。
- Redis、Kafka、Elasticsearch Testcontainers 测试。
- Controller 权限测试。
- 核心链路端到端测试。
- Agent 工具选择、权限、确认和任务完成测试。

重点测试场景：

- 重复和并发发布。
- 重复关注和取关。
- 重复点赞和 Kafka 重复投递。
- Redis 数据损坏后的重建。
- ES 和向量索引丢失后的回灌。
- 非公开内容权限。
- Agent 未经确认执行敏感操作。

## 9.3 可观测性

- Actuator 健康检查。
- Micrometer + Prometheus + Grafana。
- HTTP Trace ID。
- 数据库连接池指标。
- Redis 和本地缓存命中率。
- Kafka 消费延迟与失败数量。
- Outbox 堆积数量。
- AI 模型耗时、Token、费用和失败率。
- RAG 检索耗时、召回数量与引用命中率。

## 9.4 性能与容量证明

所有性能结论必须来源于可复现压测，不写没有测量依据的理论数字。

仓库应提供：

- 压测脚本。
- 测试环境说明。
- 并发量与数据规模。
- P50/P95/P99。
- 错误率。
- 缓存命中率。
- Redis 内存占用。
- Kafka 消费积压与恢复时间。

## 10. 里程碑

### M1：传统业务正确性基础

- 知文状态机和发布幂等。
- 可见性权限。
- 关注取关幂等。
- 正确异常与 HTTP 状态。
- Flyway 基线。
- 核心集成测试。

## 11. 第一批开发任务

第一批从知文生命周期开始，范围固定为：

1. 新增 `KnowPostStatusEnums` 和 `KnowPostVisibilityEnums`。
2. 将 KnowPost 业务中的状态、可见性字符串收敛到 enum 边界。
3. 发布 SQL 增加原状态条件，保证并发与重复发布幂等。
4. 删除 SQL 增加原状态条件，避免重复副作用。
5. 发布前校验标题、正文、摘要和可见性。
6. 发布计数只在真实状态变化后更新。
7. Outbox 插入失败时回滚业务事务，不再吞异常。
8. 补充发布、重复发布、越权发布、删除和 Outbox 失败测试。
9. 保持现有前端 API 兼容；如响应语义变化，同步更新接口文档。

第一批明确不包含：人工审核 UI、评论、通知、Agent 和大规模包迁移。

## 12. 完成定义（Definition of Done）

一个开发任务只有同时满足以下条件才算完成：

- 业务规则和异常语义明确。
- Controller、Service、Mapper 职责正确。
- 数据库变更有 Flyway 脚本。
- 新增或修改接口有 DTO/VO 和接口文档。
- 单元测试与必要的集成测试通过。
- Docker 环境能够构建并运行。
- 不提交密钥、依赖目录和运行数据。
- `git diff --check` 通过。
- 变更提交到 `dev`，阶段验收后再合并到 `main`。

## 13. 明确不做的事情

- 不为了展示架构拆分微服务。
- 不引入 API Gateway。
- 不使用 Java record。
- 不做无限自主运行的通用 Agent。
- 不在没有数据和评测依据时引入 GraphRAG 或多 Agent。
- 不用缓存代替数据库事实。
- 不用吞异常的方式维持表面可用。
- 不写无法通过测试、监控或压测证明的性能结论。

# 面试讲解：点赞/收藏可靠链路

> 对应版本：知光 `dev` 分支第五批后端重构

## 1. 30 秒面试说法

原系统把 Redis 位图当作点赞收藏的唯一事实，修改位图后异步发送 Kafka，而且序列化或发送失败会被直接吞掉。这会造成状态已经改变但计数事件永久丢失，也无法可靠实现“我的点赞”和“我的收藏”。我新增了 MySQL `content_actions` 事实表，行为状态与 Outbox 在同一事务提交；Canal 和 Kafka 将事件至少一次投递给行为投影消费者。消费者始终读取数据库当前状态，幂等重建 Redis 位图、用户反向索引和精确计数，因此重复、乱序和 Redis 数据丢失都可以恢复。

## 2. 同步命令链

```text
POST /api/v1/action/like | unlike | fav | unfav
  ↓ JWT 获取 userId
ActionEntityTypeEnums 白名单校验
  ↓ 当前仅支持 knowpost
校验 entityId 为正整数
  ↓
KnowPostPermissionService.requireReadable
  ↓ 统一复用 PUBLIC/FOLLOWERS/SCHOOL/PRIVATE/UNLISTED 权限
content_actions 条件状态迁移
  ├─ 新行为：唯一键保护的 INSERT IGNORE
  ├─ 恢复行为：action_status 0 -> 1
  ├─ 取消行为：action_status 1 -> 0
  └─ 重复命令：影响 0 行，不生成事件
  ↓ 同一个 MySQL 事务
写入 content_action Outbox
  ↓
事务提交后立即返回 changed + 目标状态
```

唯一约束为：

```text
(user_id, entity_type, entity_id, action_type)
```

因此同一个用户对同一个实体的同一种行为最多只有一条事实记录，并发请求也只有一个能完成真实状态变化。

## 3. 异步投影链

```text
content_actions + Outbox 同事务提交
  ↓ MySQL binlog
Canal -> canal-outbox Topic
  ↓ action-outbox-consumer
consumer + eventId 去重
  ↓
重新读取 content_actions 当前事实
  ├─ 更新分片位图 bm:{metric}:{entityType}:{entityId}:{chunk}
  ├─ 更新用户反向 ZSet ua:{metric}:{userId}
  ├─ 从 MySQL COUNT 得到精确内容计数并覆盖 SDS
  ├─ 根据精确内容计数重建作者获赞/获藏数
  └─ 删除相关 Feed 页面缓存
  ↓
成功后提交 Kafka 位点
失败重试三次后进入 canal-outbox.DLT
```

消费者不依赖事件中的 `+1/-1` 直接累加，而是查询数据库当前事实并覆盖投影。假设用户快速执行“点赞 -> 取消”，即使旧的点赞事件稍后重放，消费者看到的数据库状态仍是未点赞，最终投影不会被旧事件改回去。

## 4. 为什么仍保留 Redis 位图

MySQL 负责正确性，Redis 负责读取性能：

- 详情和 Feed 判断当前用户是否点赞/收藏时，使用分片位图 `GETBIT`。
- 用户行为反向索引使用 ZSet，支持按操作时间倒序读取。
- 内容点赞数、收藏数使用固定结构 SDS，单次 GET 可读取多个指标。
- Redis 全量丢失时，计数可以从 `content_actions` 事实表重新 COUNT，位图和反向索引可通过 Outbox 重放重建。

位图分片键通过显式索引集合维护，不再在线执行 Redis `KEYS`。

## 5. “我的点赞/收藏”

新增接口：

- `GET /api/v1/action/likes`
- `GET /api/v1/action/favorites`

接口支持 `limit` 和 `offset`，范围限制为 1～100。查询以 MySQL 事实表为准，使用索引：

```text
(user_id, action_type, action_status, updated_at, id)
```

Redis ZSet 是高性能反向投影，可以继续用于后续游标分页和个性化推荐，但不能替代数据库事实。

## 6. 数据库迁移

项目引入 Flyway，迁移脚本为：

```text
db/migration/V1__create_content_actions.sql
```

已有数据库通过 `baseline-on-migrate` 建立版本基线后执行增量迁移；全新环境仍由基础 schema 初始化，再由 Flyway 管理后续版本。这样数据库修改不再依赖开发者手工复制 SQL。

## 7. 高频追问

### 为什么不直接要求 Kafka exactly-once？

业务事实提交在 MySQL，Kafka 只负责传播变化。Outbox 解决业务提交与消息产生的原子性；至少一次投递配合幂等、事实型投影即可得到最终一致性，比跨 MySQL、Kafka、Redis 追求端到端 exactly-once 更清晰可验证。

### 为什么取消操作也保留数据库行？

逻辑状态允许幂等恢复，避免频繁删除和重新插入，也保留首次创建时间与最近状态变化时间。唯一键始终存在，并发恢复只会有一次 `0 -> 1`。

### Redis 已经 AOF 持久化，为什么还要 MySQL？

AOF 能降低 Redis 重启丢失概率，但不能解决“位图成功、Kafka 发送失败”的跨系统原子性，也不适合承担可审计的行为列表事实。MySQL 行为表提供事务、唯一约束、分页索引和可恢复来源，Redis 回到加速层职责。

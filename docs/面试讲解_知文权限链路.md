# 面试讲解：知文统一权限链路

> 对应版本：知光 `dev` 分支第二批后端重构

## 1. 30 秒面试说法

原系统的详情、Feed、搜索和 RAG 分别判断权限，规则不一致，而且详情命中缓存时可能绕过数据库权限判断，搜索索引延迟期间也可能短暂暴露刚改成私密的内容。我新增统一的 `KnowPostPermissionService`，明确五类可见性；详情和 RAG 在读取缓存、向量检索及调用模型之前先鉴权。Feed 在 SQL 层只查询公开已发布内容。搜索同时使用 Elasticsearch 过滤和 MySQL 批量复核，既防止旧索引泄漏，也避免逐条查询造成 N+1。

## 2. 权限矩阵

| 可见性 | 作者 | 匿名用户 | 已登录普通用户 | 关注者 | 同校用户 | Feed/搜索 |
|---|---:|---:|---:|---:|---:|---:|
| `PUBLIC` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| `FOLLOWERS` | ✓ | ✗ | ✗ | ✓ | 视关注关系 | ✗ |
| `SCHOOL` | ✓ | ✗ | 视学校 | 视学校 | ✓ | ✗ |
| `PRIVATE` | ✓ | ✗ | ✗ | ✗ | ✗ | ✗ |
| `UNLISTED` | ✓ | 持链接可读 | 持链接可读 | 持链接可读 | 持链接可读 | ✗ |

共同前提：非作者只能读取 `published` 状态；`deleted` 统一按不存在处理。

## 3. 详情读取链路

```text
GET /api/v1/knowposts/detail/{id}
  ↓
提取可选 JWT 用户 ID
  ↓
KnowPostPermissionService.requireReadable
  ├─ 不存在或已删除 → 404
  ├─ 作者本人 → 允许，包括自己的草稿
  ├─ 非 published → 403
  ├─ PUBLIC / UNLISTED → 允许直接访问
  ├─ FOLLOWERS → 查询有效关注关系
  ├─ SCHOOL → 比较作者与访问者的非空学校
  └─ PRIVATE → 拒绝
  ↓
权限通过后才读取 Caffeine / Redis 详情缓存
  ↓
叠加当前用户点赞、收藏状态后返回
```

关键点是“先鉴权，再读缓存”。缓存只能提升数据读取速度，不能成为权限事实来源，否则私密内容可能因为公共缓存命中而绕过校验。

## 4. Feed 与搜索链路

公共 Feed 在 MySQL SQL 层固定要求：

```sql
status = 'published' AND visible = 'public'
```

搜索使用两层防线：

```text
Elasticsearch 查询
  ├─ status = published
  └─ visible = public
       ↓
取得候选 ID
       ↓
一次 MySQL IN 批量复核当前状态与可见性
       ↓
只组装仍然 published + public 的结果
```

为什么还要查一次 MySQL：用户把公开知文改成私密后，MySQL 已经生效，但 Outbox、Canal、Kafka 到 ES 更新存在短暂延迟。只相信 ES 会产生权限时间窗。批量复核把 MySQL 主数据作为最终裁决，同时避免每条结果单独查询造成 N+1。

可见性变化会写入 `KnowPostVisibilityChanged` Outbox，异步清理或重建搜索文档。非公开内容在搜索索引中只保留软删除占位，不保存可搜索正文和标题。

## 5. RAG 权限链路

```text
GET /api/v1/knowposts/{id}/qa/stream
  ↓
统一权限校验
  ↓ 通过
确保该知文向量索引存在
  ↓
按 postId 筛选召回切片
  ↓
组装提示词并调用模型
  ↓
SSE 流式返回
```

权限校验发生在向量检索和模型调用之前，因此未授权请求不会消耗模型额度，也不会获取任何上下文。手动重建向量索引接口要求 JWT，并再次验证当前用户是知文作者。`topK` 与 `maxTokens` 设置上下限，避免无界资源消耗。

## 6. 高频追问

### 为什么搜索要 ES 过滤后再查 MySQL？

ES 是最终一致的查询投影，不是权限事实来源。双重过滤兼顾搜索性能和权限实时性；正常情况下 ES 已过滤掉绝大多数内容，MySQL 只用一次 `IN` 查询复核一页候选。

### 为什么不把所有权限判断都写进 SQL？

Feed 的公开规则适合下推 SQL；详情和 RAG 还涉及作者、关注关系和学校规则，需要统一的领域服务。物理查询可以按场景优化，但业务语义必须由一个服务定义。

### `UNLISTED` 和 `PRIVATE` 有什么区别？

`UNLISTED` 是持有链接即可访问，但不能通过 Feed、搜索和联想发现；`PRIVATE` 只有作者自己能访问。

### 缓存为什么不能直接缓存“有权限”？

关注关系、学校和可见性都可能变化。直接缓存最终授权结果容易产生撤权延迟。当前先以数据库保证正确性，后续若权限查询成为热点，再设计短 TTL 和主动失效。

### 当前边界是什么？

搜索已经有索引过滤和数据库复核，但关注关系当前依赖异步关系投影；后续需要继续完善关系事件的幂等、重试和一致性监控。向量检索仍是宽召回后按 `postId` 过滤，下一阶段 AI 重构会改为向量库原生元数据过滤与混合检索。

# 面试讲解：知文生命周期与可靠发布链路

> 对应版本：知光 `dev` 分支第一批后端重构  
> 适用场景：项目介绍、业务链路追问、事务与幂等追问

## 1. 一句话定位

知光是一个以“知文”为核心的知识社区。第一批重构没有继续堆功能，而是先把最关键的“草稿发布—异步投影—删除”链路改造成有状态约束、事务一致性和幂等保障的业务闭环。

## 2. 30 秒面试说法

原实现只按 ID 和作者更新发布状态，重复请求会重复增加发文数；Outbox 写入失败还会被吞掉，造成 MySQL 已发布但搜索侧永远收不到事件。我把知文状态和可见性收敛成枚举，发布前校验标题、正文、摘要和可见性，SQL 使用 `draft → published` 条件更新解决并发发布。知文更新和 Outbox 在同一个 MySQL 事务中，Outbox 失败会让整个事务回滚。计数和 RAG 预索引通过 `AFTER_COMMIT` 监听器在提交后执行，避免数据库回滚但外部副作用已经发生。重复发布和重复删除按当前状态直接幂等返回。

## 3. 新版业务链

```text
客户端发布请求
  ↓
Controller：解析 JWT、校验参数、调用 Service
  ↓
KnowPostService.publish（MySQL 事务）
  ├─ 按 ID 查询知文
  ├─ 校验知文存在与作者权限
  ├─ 已发布：幂等成功返回
  ├─ 非草稿：返回 409 状态冲突
  ├─ 校验标题、正文对象、正文 URL、摘要和可见性
  ├─ SQL 条件更新：WHERE id=? AND creator_id=? AND status='draft'
  │    └─ 影响行数为 0：说明并发状态已变化，返回 409
  ├─ 同事务写入 Outbox：KnowPostPublished
  └─ 发布本地生命周期事件
       ↓
MySQL 提交成功
  ├─ AFTER_COMMIT：发文数 +1
  ├─ AFTER_COMMIT：触发 RAG 预索引（失败不反向污染主事务）
  └─ Canal 订阅 Outbox binlog
       ↓
Kafka canal-outbox
       ↓
搜索消费者幂等 upsert Elasticsearch 文档
```

删除链路与发布链路对称：先读取并校验当前状态，`WHERE status = 当前状态` 条件软删除，再同事务写入 `KnowPostDeleted`。只有原状态为 `published` 时，事务提交后才执行发文数 `-1`；已删除内容重复删除直接幂等成功。

## 4. 为什么能防重复发布

不能只依赖“先查后改”，因为两个并发请求可能同时查到 `draft`。真正的并发控制在更新 SQL：

```sql
UPDATE know_posts
SET status = 'published', publish_time = NOW(), update_time = NOW()
WHERE id = ? AND creator_id = ? AND status = 'draft';
```

MySQL 对同一行串行更新。第一个请求把状态改为 `published` 后，第二个请求的条件不再成立，影响行数为 0，因此不会写第二条 Outbox，也不会再次增加发文数。这是一种基于状态条件的乐观并发控制，不需要额外分布式锁。

## 5. 事务一致性规则

- `know_posts` 状态更新与 `outbox` 插入共用一个本地事务。
- Outbox 序列化或写库失败会抛出异常，不再静默吞掉，因此知文状态一并回滚。
- Redis、RAG、Elasticsearch 等外部系统不放进 MySQL 事务，避免长事务和跨系统假事务。
- 本地提交后事件只承担“快速投影”，Outbox 承担可恢复的跨系统事实传递。

这里需要如实说明当前边界：搜索同步已经由 Outbox、Canal、Kafka 驱动；发文数与 RAG 的 `AFTER_COMMIT` 处理目前是尽力而为，进程在提交后、执行前宕机时可能漏处理。下一阶段会让它们也由带事件 ID 的 Outbox 消费者处理，并增加去重、重试、死信与重放能力。

## 6. HTTP 与业务错误语义

| 场景 | 错误码 | HTTP 状态 |
|---|---|---:|
| 知文不存在 | `KNOW_POST_NOT_FOUND` | 404 |
| 不是知文作者 | `KNOW_POST_FORBIDDEN` | 403 |
| 状态非法或并发更新失败 | `KNOW_POST_STATE_CONFLICT` | 409 |
| 标题、正文、摘要等不完整 | `KNOW_POST_INCOMPLETE` | 400 |

这样前端不需要解析中文提示，可以根据稳定错误码决定刷新、跳转或展示补全表单。

## 7. 状态与可见性模型

知文状态预留为：

```text
DRAFT → PENDING_REVIEW → PUBLISHED → OFFLINE → DELETED
                  ↘ REJECTED → DRAFT
```

第一批实际开放的是草稿发布和任意非删除状态的软删除；审核流将在后续启用。可见性枚举包括 `PUBLIC`、`FOLLOWERS`、`SCHOOL`、`PRIVATE`、`UNLISTED`。第一批完成了取值收敛，下一批会建立统一权限服务，解决详情、Feed、搜索和 RAG 的权限一致性。

## 8. 高频追问与回答

### 为什么不用 Redis 分布式锁？

发布竞争只发生在 MySQL 的同一聚合行上，带原状态条件的单条更新已经能原子判定胜者。分布式锁会增加续期、超时和锁服务可用性问题，却不能替代数据库最终写入条件。

### 为什么不直接在事务里调用 Elasticsearch？

MySQL 事务无法原子提交 Elasticsearch。直接调用会出现 ES 成功但 MySQL 回滚，或 MySQL 成功但 ES 失败。Outbox 先把“已发布”事实和业务数据一起提交，再异步构建搜索投影。

### Outbox 为什么比“提交后直接发 Kafka”可靠？

直接发 Kafka 存在数据库已经提交但进程在发送前宕机的窗口。Outbox 把待发送事件作为数据库记录持久化，Canal 可以从 binlog 继续捕获和发送。

### 为什么重复发布返回成功，而并发失败返回 409？

请求到达时已经是 `published`，可以判断目标状态已经达成，所以幂等成功。请求读取到 `draft` 后条件更新却为 0，说明处理中发生并发状态变化，客户端应刷新，因此返回 409。

### 为什么 RAG 不是发布事务的一部分？

向量化和外部模型调用耗时高、失败面大，放在事务中会长期占用连接和行锁。发布事务只提交业务事实，索引是可重建的派生数据。

### 当前还缺什么？

核心发布原子性已经完成，但完整生产级方案还需要统一权限服务、消费者事件去重、失败重试和死信、Outbox 状态与重放后台、真实 MySQL/Kafka/Redis 集成测试，以及操作审计日志。

## 9. 面试表达原则

- 先讲业务故障，再讲技术选择，不从组件名称开始背诵。
- 明确区分“主数据”和“可重建投影”：MySQL 知文是主数据，计数、搜索索引、向量索引是投影。
- 主动说明方案边界，不把 `AFTER_COMMIT` 说成可靠消息。
- 强调条件更新解决的是并发正确性，Outbox 解决的是跨系统最终一致性，两者不是同一个问题。
- 用测试结果作证：覆盖重复发布、内容不完整、并发状态变化、Outbox 失败、发布后投影、发布内容删除和重复删除。
